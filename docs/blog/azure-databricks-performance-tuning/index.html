Cutting Pipeline SLAs from 6 Hours to Under 3

November 15, 2025 10 min read

A credit card portfolio migration was landing millions of records a day and finishing in just over six hours. The business needed same-day credit risk reporting, which meant finishing in three. Here is what moved the number, and what I spent time on that turned out not to matter.

Measure before touching anything

The instinct is to start adding cluster nodes. Resist it for one run and read the Spark UI instead. The stage timeline tells you whether you are bound by shuffle, by skew, by small files, or simply by doing too much work.

In our case the profile was unambiguous: two stages accounted for roughly 70% of wall clock, both of them joins, and both showing a handful of tasks running ten times longer than the median. That is skew, and no amount of extra hardware fixes skew — you just pay more for the same stragglers.

Small files were the quiet tax

The upstream feed arrived as thousands of small files per day from an S3 landing zone. Spark was spending a significant share of its time on file listing and task scheduling overhead rather than on actual computation — thousands of tasks each processing a few megabytes.

Compaction at the Bronze boundary was the single cheapest win. Delta's optimize handles this directly, and auto-compaction keeps it from regressing:

-- one-time cleanup
OPTIMIZE bronze.transactions
WHERE _ingest_date >= current_date() - 7;

-- keep it from coming back
ALTER TABLE bronze.transactions SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',
  'delta.autoOptimize.autoCompact'   = 'true'
);

Target file sizes in the 128MB–1GB range. Smaller and you drown in overhead; much larger and you lose parallelism and the ability to prune effectively.

Partitioning: fewer, coarser partitions

The original design partitioned by date and account segment, which produced a large number of tiny partitions. Over-partitioning is a common and expensive mistake — it looks like careful design and behaves like fragmentation.

We dropped to a single date partition and used Z-ordering for the secondary access pattern, which gives you data skipping without the directory explosion:

OPTIMIZE silver.transactions
ZORDER BY (account_id, merchant_id);

The rule of thumb that has served me well: partition on the column that appears in nearly every query's filter — usually a date — and only if partitions will hold at least a gigabyte. Everything else is a Z-order candidate.

Handling the skew directly

A small number of high-volume merchant accounts dominated the join keys. Adaptive Query Execution handles a lot of this automatically on recent runtimes, and enabling skew join handling cost us nothing:

spark.conf.set("spark.sql.adaptive.enabled", "true")
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")

For the dimension joins, broadcasting the smaller side removed the shuffle entirely. Worth checking your actual table sizes rather than trusting the default threshold — several of our dimensions were comfortably broadcastable and were not being broadcast because statistics were stale. Running ANALYZE TABLE fixed that for free.

Caching: useful in exactly one place

Caching is the most over-applied optimization in Spark. It only pays when a dataset is genuinely reused across multiple actions and fits comfortably in memory. We had one such dataset — a conformed account dimension referenced by six downstream transformations — and caching it helped measurably.

Everywhere else, caching made things worse by evicting data the executors actually needed. If you cannot name the specific second action that reads the cached frame, do not cache it.

Cluster sizing came last

Only after the logical work was reduced did cluster configuration become worth tuning. The useful changes were unglamorous: fewer, larger workers rather than many small ones (less shuffle across the network), autoscaling bounded with a sensible floor so the job did not spend its first minutes scaling up, and a runtime upgrade that brought Photon and better AQE behaviour.

Had we started here, we would have spent considerably more on compute to run the same inefficient plan slightly faster. Tuning the cluster before tuning the query is how cloud bills grow.

What didn't help

  • ▸Manually setting spark.sql.shuffle.partitions — AQE coalesces better than a static guess.
  • ▸Repartitioning defensively before writes, which added a full shuffle to avoid a problem optimized writes already solved.
  • ▸Rewriting PySpark into Spark SQL for speed. The Catalyst optimizer treats them the same; pick whichever is more readable.

Order of operations

If I were handed the same problem again, I would work it in this order, and I would stop as soon as the SLA was met:

  • ▸Read the Spark UI and identify the two stages that dominate wall clock.
  • ▸Fix file sizes. Compaction is cheap and almost always helps.
  • ▸Simplify partitioning; move secondary keys to Z-order.
  • ▸Enable AQE and skew handling; refresh statistics so broadcasts trigger.
  • ▸Cache only datasets with a named second reader.
  • ▸Only then resize the cluster.

Six hours to under three, and the compute bill went down rather than up — because most of the gain came from doing less work, not from buying more machines.
