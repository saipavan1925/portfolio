A Practical Guide to Medallion Architecture on Azure Databricks

January 28, 2026 12 min read

Bronze, Silver, Gold is three boxes and two arrows. Every vendor diagram makes it look settled. The hard part is not the picture — it is deciding what belongs in each layer when a real source system starts sending you malformed dates at 2am.

Bronze: resist the urge to fix anything

Bronze is the landing zone. Raw data, as it arrived, with provenance attached. The discipline here is negative — it is about what you don't do. No type coercion, no deduplication, no business rules, no dropping of bad rows.

This feels wrong the first time. You can see the broken record and you have the fix right there. Do not apply it in Bronze. The moment Bronze stops being a faithful copy of the source, you lose your ability to replay. And you will need to replay — because in six months you will discover a transformation bug and need to rebuild Silver from scratch without going back to a source system that has since been decommissioned.

What Bronze should add is metadata about the arrival itself:

bronze.transactions
  ├─ <source columns, original types, unmodified>
  ├─ _ingest_timestamp    timestamp
  ├─ _source_file         string
  ├─ _batch_id            string
  └─ _ingest_date         date      -- partition key

Partition Bronze by ingestion date, not by business date. Business dates are untrustworthy at this stage, and ingestion date is what you need when you are answering "what did we receive on the day the numbers went wrong?"

Silver: where the real work happens

Silver is cleansed, conformed, deduplicated, and typed. This is the layer most teams under-invest in and later regret. If Silver is good, Gold is almost trivial. If Silver is weak, you will find the same cleanup logic copy-pasted across fifteen Gold tables, each drifting from the others.

Silver is where schema enforcement belongs. Delta Lake gives you this directly:

(df.write
   .format("delta")
   .mode("append")
   .option("mergeSchema", "false")   # fail loudly on drift
   .saveAsTable("silver.transactions"))

Set mergeSchema to false in Silver and let writes fail when the source changes shape. An alert at 2am is unpleasant; silently absorbing a renamed column and serving wrong numbers for a quarter is much worse. Schema evolution should be a reviewed decision, not an automatic one.

The deduplication pattern that holds up under late-arriving data:

from pyspark.sql import Window
from pyspark.sql import functions as F

w = (Window
     .partitionBy("transaction_id")
     .orderBy(F.col("source_updated_at").desc(),
              F.col("_ingest_timestamp").desc()))

silver = (bronze
          .withColumn("_rn", F.row_number().over(w))
          .filter(F.col("_rn") == 1)
          .drop("_rn"))

Note the two-level ordering. Sorting only by the source timestamp breaks when a source system re-sends a record with an identical timestamp; falling back to ingestion time makes the result deterministic.

Gold: shaped for a consumer, not for elegance

Gold is business-level aggregation — the tables analysts and dashboards actually query. The temptation is to build one beautiful, normalized Gold model that serves everyone. Resist it. Gold tables should be denormalized and purpose-built. It is entirely reasonable to have three Gold tables covering overlapping data if three teams ask three different questions.

Duplication in Gold is cheap. Contention over a single shared model is expensive, because every change requires consensus from every consumer.

Reconciliation: the part nobody puts in the diagram

Running millions of records daily, "the pipeline succeeded" is not the same as "the data is right." A job can complete happily having processed a truncated file. Every layer boundary needs a reconciliation check that runs as part of the pipeline, not as a separate report somebody reads on Thursdays.

  • ▸Count reconciliation — source rows versus Bronze rows per batch, exact match expected.
  • ▸Checksum reconciliation — sums of key financial columns carried through Bronze → Silver → Gold. Any divergence is explained by a documented rule or it is a bug.
  • ▸Volume anomaly detection — today's row count against a trailing average. A 40% drop usually means a partial file, not a quiet business week.
  • ▸Referential checks — orphaned foreign keys surfacing at the Silver boundary, where you can still trace them back.

Write these as pipeline tasks that fail the run. A check that only logs a warning is a check nobody will see.

Metadata-driven ingestion

Once you are past roughly ten source tables, hand-written notebooks per table stop scaling. The move is to drive ingestion from a configuration table — source location, format, target, partition keys, quality rules, SLA — and run one parameterized pipeline over it.

The payoff is onboarding time. Adding a new source becomes a configuration row and a review, measured in days rather than weeks, and every new source inherits the validation and audit behaviour of every existing one rather than reimplementing it.

The short version

  • ▸Bronze is immutable and boring. Keep it that way so you can always replay.
  • ▸Silver carries the weight. Enforce schema, deduplicate deterministically, conform types once.
  • ▸Gold serves consumers. Denormalize freely; duplication beats coordination overhead.
  • ▸Reconcile at every boundary, and make failures fail the run.
  • ▸Drive ingestion from metadata before you have fifty bespoke notebooks.
