Agentic AI in Data Engineering: Migrating 90 Stored Procedures in Days

March 12, 2026 9 min read

Legacy migration work is the least glamorous thing in data engineering and the most expensive. A bank accumulates hundreds of stored procedures and desktop workflows over a decade, each one encoding business logic nobody fully remembers. Rewriting them by hand is slow, error-prone, and very hard to staff. We replaced most of that effort with a fleet of agents.

The problem we actually had

Our target was 90 legacy SQL stored procedures and 20 Alteryx workflows feeding credit risk reporting. The destination was Databricks — Spark SQL running over Delta Lake. The naive estimate for a manual rewrite was several engineer-months, and the real cost was worse than the number suggested: every manual rewrite is a fresh opportunity to silently change a join, drop a filter, or round a number differently. On credit risk data, a silent change is the expensive kind.

What made this tractable for an LLM is that it is fundamentally a translation task with a checkable answer. We were not asking a model to invent business logic. We were asking it to re-express logic that already existed, in a dialect we could test against the original.

Why agents and not just prompts

A single prompt per procedure fails for an obvious reason: the model has no idea what the tables look like. Stored procedures reference dozens of objects, some of which are themselves views over other views. A one-shot translation hallucinates column names with total confidence.

The fix was to give the agent tools and let it work the problem in steps. Each agent could inspect the source schema, resolve dependencies, read the procedure, emit candidate Spark SQL, run it against a sample, and read the error back. That loop — generate, execute, observe, repair — is what moved accuracy from "interesting demo" to something we could put in front of a compliance team.

Agent loop (simplified)

  1. resolve_dependencies(proc)      -> table + view graph
  2. fetch_schema(tables)            -> typed column catalog
  3. generate_spark_sql(proc, schema)-> candidate translation
  4. dry_run(candidate)              -> errors | row sample
  5. if errors: repair(candidate, errors) -> goto 4
  6. reconcile(candidate, source)    -> row + aggregate diff
  7. if diff: flag_for_human()
     else:    emit + generate_tests()

Schema-aware generation

The single highest-leverage change was injecting the real schema into the generation step. Not a description of the schema — the actual typed column catalog for every object in the dependency graph, pulled live. Hallucinated column names essentially disappeared once the model could see the columns.

The second change was giving the agent the dialect differences explicitly. SQL Server and Spark SQL disagree about date arithmetic, string functions, null ordering, and implicit casting. Left to infer these, the model produces code that parses and returns subtly wrong answers. Given a short, concrete mapping of the traps, it produces code that is right the first time far more often.

Validation is the whole product

We reached 95% autonomous conversion confidence. The number people usually ask about is the 95%. The number that mattered to us was the other 5% — specifically, our ability to identifywhich 5%. A migration tool that is 95% correct and cannot tell you which parts are wrong is worse than useless, because it moves the failure from your build to your regulator.

So every translation had to clear three gates before it was accepted:

  • ▸Execution — the generated Spark SQL runs without error against real schemas.
  • ▸Reconciliation — row counts and aggregate checksums match the source procedure output on the same input window.
  • ▸Generated tests — the agent authors unit tests covering null handling, boundary dates, and edge-case joins, which then live on in the repo.

Anything failing a gate was routed to a human with the diff attached. That is the real output of the system: not "here is your code" but "here is your code, here is the evidence it is correct, and here are the four cases where I am not sure."

Lineage as a side effect

An unplanned benefit: because the agents had already resolved every dependency to translate the logic, we had a complete source-to-target map almost for free. We captured it and handed compliance teams end-to-end lineage from on-prem systems to Azure targets — something that had previously been maintained by hand in a spreadsheet, and was always out of date.

What I would tell someone starting this

  • ▸Pick a domain where correctness is checkable by machine. Translation qualifies; greenfield design does not.
  • ▸Spend your effort on the validation harness, not on prompt wording. The harness is what earns trust.
  • ▸Give agents live schema access. Context beats cleverness every time.
  • ▸Design for the failures. Routing uncertain cases to humans with good diffs is a feature, not an admission of defeat.
  • ▸Capture the metadata the agents generate along the way. Lineage, documentation, and tests are often worth as much as the migration itself.

Months of manual engineering became days of supervised automation. The engineering judgment did not disappear — it moved from typing out translations to designing the system that checks them.
